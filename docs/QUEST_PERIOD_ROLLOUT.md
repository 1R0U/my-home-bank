# 定期クエストの初回移行（Issue #263 / PR #499）

## 既存タスクの確認

稼働中のSupabaseのSQL Editorで、[適用前確認SQL](../tests/sql/quest_period_preflight.sql)を実行する。読み取り専用で、家庭・区分・状態別の件数、同名の候補、対象のIDと申請状況を確認できる。期間列を追加する前にも実行できる。

完了済みを再び繰り返すか、同名のどの行を引き継ぐかは、結果を見て決める。タイトルが同じでも、内容や報酬が違うことがあるため、自動で統合・削除しない。

2026-10-24の稼働DB確認では、同じ家庭のデイリー5件（未着手3件・進行中2件、完了済みなし）があり、同名「あ」は3件だった。ユーザー指定により、新しい100 golの「あ」1件と「い」「か」を繰り返しに引き継ぐ。

| 対象ID | 内容 | 引き継ぎ |
| --- | --- | --- |
| `b1731de0-5259-46aa-9734-31240983cd63` | あ・100 gol・未着手 | 繰り返す |
| `f95ddcd8-4a90-4348-8a6c-b6e849785ab9` | い・100 gol・進行中 | 繰り返す |
| `0f0eedf5-ab85-4d0f-9b5e-d94a4b4a5a98` | か・50 gol・未着手 | 繰り返す |
| `427714d8-a0d3-4c82-af5d-92220c2611fc` | あ・10 gol・未着手 | 今ある1回分を保持し、繰り返さない |
| `de98a7ce-ae93-4be6-aea8-4edc14f79d55` | あ・10 gol・進行中 | 今ある1回分を保持し、繰り返さない |

対象外の2件は期間と設定元を付けず、完了申請・承認を引き続き行える。状態・担当・報酬・履歴は変更せず、完了しても次の実施は作らない。ID・区分・タイトル・報酬の組み合わせが違う場合、3件の「あ」が異なる家庭に属する場合、または3件の一部だけが存在する場合は補完を停止する。家庭IDは固定せず、確認済みの100 golの「あ」から取得する。新規環境に3件とも存在しない場合はこの個別指定を使わない。

2026-10-25の適用時に、以前のSQLが固定していた家庭IDと実データが一致せず、補完が停止した。1本目は適用済み、2本目はこの検査で失敗して未適用であることを確認し、2本目だけを上記の照合に修正した。1本目は再実行せず、修正した2本目から再開する。

同日の追加確認で完了済みデイリーが見つかり、ユーザー指定により次のように引き継ぐ。再開する3件は家庭IDを固定せず、お風呂掃除のIDから取得した家庭にそろっていること、ID・区分・タイトル・報酬・完了状態が一致することを検査する。

| 対象ID | 内容 | 引き継ぎ |
| --- | --- | --- |
| `f8f409e5-4794-4b5a-a941-bb2500123aef` | お風呂掃除・100 gol | 次の終了時刻から繰り返す |
| `31a440bb-a066-4c39-9b1e-245f97f45d25` | 宿題・50 gol | 次の終了時刻から繰り返す |
| `56d11b9d-9e3a-4de8-ac40-0f3a702dabe9` | 部屋の掃除・100 gol | 次の終了時刻から繰り返す |
| `a59f40bf-90e2-4afc-89a2-068d756fc998` | あ・10 gol | 完了履歴だけ残し、繰り返さない |
| `ea9a1523-bd3c-4dfd-bfef-81bb5e095cc9` | い・10 gol | 完了履歴だけ残し、繰り返さない |
| `012a4c92-1bf0-4672-82c1-c45ef5d6acb3` | う・10 gol | 完了履歴だけ残し、繰り返さない |

繰り返す完了済み3件は、移行時点の現在の回を完了済みとして扱い、次の終了時刻（日本時間00:00）から新しい回を作る。完了・担当・報酬・承認履歴と、お財布・金庫の残高を変更しない。

別家庭の「ヤマダ電機」「掃除」も完了済みとして残っていたため、2026-10-25にユーザーが「完了済みは家事3件だけ繰り返す」と指定した。全家庭で、指定3件以外の未移行（設定元が未設定）の完了済みデイリー・ウィークリーは、個別のID追加なしで履歴として残す。既に期間・設定元を持つ完了済みはこの対象に含めず、設定済みの繰り返しを止めない。

バックフィルは、古い10 golの「あ」2件と、履歴として残す未移行の完了済みを除外し、指定3件に期間を補う。繰り返し対象に同じ家庭・区分・タイトルの複数候補があれば停止し、先に補った完了済み3件の期間も同じDOブロック内で取り消す。履歴として残す行の状態・担当・金額・申請履歴は一切書き換えない。

確認済みの対象は、進行・申請・報酬を保持し、デイリーを00:00終了、ウィークリーを月曜始まりとして引き継ぐ。

## アプリ更新とDB適用の順序

旧クライアントは `quests` を直接取得するため、期間別の実施が増えると過去の回も表示してしまう。新クライアントは新しいRPCと期間列を使うため、DB適用前には利用できない。両者を混在させたまま運用しない。

1. 適用前確認の結果・引き継ぐ対象・移行SQLを確定する。
2. 更新済みアプリを配信できる状態にし、接続している全端末で利用を一時停止する。
3. PRのマイグレーション4本を番号順に適用し、[スキーマ検証SQL](../tests/sql/verify_remote_schema.sql)がすべてOKになることを確認する。途中で停止した場合は利用を再開せず、既に適用したファイルを確認してから対応する。
4. [配布手順](DISTRIBUTION.md)に従い、まずinternalで更新を確認し、その後productionへ配信する。mainへのマージだけではEAS Updateは配信されない。
5. 端末ごとに更新の適用を確認してから利用を再開する。EAS Updateで全端末が即時に更新されるとは想定しない。更新できていない端末では旧アプリを使い続けない。

新しい期間の受注、前の期間の申請の承認、子供ごとの担当、残件数を確認する。問題があれば配信と利用再開を止め、申請・報酬履歴を削除して戻すことはしない。
