# 自動積立預金の運用（Issue #162）

既存の手動預金を残し、`savings_accounts` に別口座を作ります。子どもは銀行の「自動積立預金」から積立額・停止・引き出しを操作し、親はローン画面の「子どもの自動積立預金・積立日設定」から家庭全体を確認できます。

## 定期実行

`20260927000000_create_automatic_savings.sql` と `20260927000100_schedule_automatic_savings.sql` を通常のマイグレーションとして適用します。本番適用前にDBテストを実行してください。

後者は [Supabase Cron](https://supabase.com/docs/guides/cron) の `pg_cron` が配布されている環境で拡張を有効にし、`automatic-savings-hourly` を毎時0分に登録します。処理日付は日本時間なので月初・積立日の日本時間0時から対象になります。端末でアプリを開く必要はありません。pg_cronが配布されていない素のPostgreSQLでは通知を出してジョブ登録を省略します。その環境を運用に使う場合は、DB所有者権限の外部スケジューラから同関数を毎時実行する必要があります。

適用後にDB管理者が以下を確認します。

```sql
select jobname, schedule, command, active from cron.job
where jobname = 'automatic-savings-hourly';
select status, return_message, start_time, end_time from cron.job_run_details
where jobid = (select jobid from cron.job where jobname = 'automatic-savings-hourly')
order by start_time desc limit 10;
```

失敗原因を解消した後の手動再実行は、DB管理者が `select private.run_savings_schedule();` を実行します。アプリ利用者にはこの関数の実行権限も処理時刻を指定する権限も付与しません。画面の取得・設定・引き出し時にも所属家庭の未処理分を処理するため、一時的な定期実行失敗から復旧できます。

## 月次処理と遅延

- 過去月の利息を古い順に確定し、その後に期日到来済みの積立を実行します。平均残高は入出金の金額と実際の記帳時刻から計算します。
- 定期処理が月をまたいで停止していた場合、未処理の積立月を古い順に実行します。各回は実行時のお財布残高が上限です。停止期間中に移動したことにはせず、復旧時刻で記帳します。複数月分が同時に移動する可能性があります。
- 設定変更前に到来済みの処理を旧設定で確定します。積立日の変更で今月の期日が過去になった場合、まだ今月分を処理していなければその場で実行します。処理済みの月は再実行しません。
- 金利は各対象月の利息を実際に処理する時点の金庫比率で固定し、同じ家庭の子どもには同じ金利を適用します。遅延時も過去の金庫残高を推測しません。
- 家庭全員の利息合計が支払い可能な額を超える場合、全員の支払いを見送り、`reserve` を保存します。部分的な利息支払い・後日追払いはしません。金庫の最低準備金は既存の金庫処理と同じ切捨て計算です。
- 複利にはせず、支払い済みの利息は翌月以降の平均残高から除外します。過去月分の利息が遅れて入った場合も、入金以前へ遡って残高を増やしません。
- 初回の積立設定が期日を過ぎていれば翌月からです。部分積立・空残高・停止は正常な確定結果で、通信やDBの失敗とは区別します。

各資金移動は残高・経済台帳・既存履歴・月次結果を同一トランザクションで更新します。再実行は保存済み結果で重複を防ぎ、引き出しは本人と操作キーで重複を防ぎます。処理途中にSQLエラーがあれば全体がロールバックします。

## 検証

`tests/sql/savings_assertions.sql` は積立日、平均残高、部分積立、スキップ、準備金、引き出し、権限、再実行を検証します。`tests/sql/run_savings_concurrency_test.sh` はPostgreSQLの2接続で積立と引き出しの並行再送を検証します。両方ともCIの DB Migration ジョブで実行します。`tests/savings*.test.*` は表示、入力、RPC引数、日付・金利の境界と通信失敗後の再送を検証します。
